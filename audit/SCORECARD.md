# Scorecard — nba-pronos

*Notes prudentes sur 10. Une bonne note n'est jamais donnée par défaut parce qu'un build ou des tests passent — chaque note reflète la profondeur réelle vérifiée dans cet audit.*

| Axe | Note /10 | Justification | Condition pour le point suivant |
|---|---|---|---|
| Compréhension fonctionnelle | 9 | Documentation interne exceptionnellement précise (journal de 359+ commits, gaps ouverts détaillés, matrice de couverture des 429 types de paris). Reconstruction indépendante du fonctionnement confirmée cohérente sur tous les modules explorés en profondeur ; le statut `POSTPONED`, seule zone d'ombre relevée, s'est avéré correct une fois vérifié (03/09/2026). | Combler la dernière zone encore "à vérifier" (2e moitié de `resolveCalculableBets.ts`). |
| Cohérence métier | 8 | Règles métier centralisées et peu dupliquées (exception : barèmes d'affichage, deadline de pari). Écarts spec/implémentation systématiquement documentés et justifiés par l'équipe elle-même, pas découverts a posteriori. | Éliminer les 4 implémentations parallèles de la deadline de pari (`BUG-002`) et synchroniser les barèmes dupliqués. |
| Architecture | 8 | Séparation lecture/écriture stricte, autorisation entièrement portée en base (RLS + `SECURITY DEFINER` + triggers), isolation propre des services externes, aucune dépendance circulaire identifiée. Limite : pas de vraie transaction SQL sur les opérations multi-tables (assumé et mitigé par idempotence sauf pour la suppression de compte). | Rendre `deleteAccountFormAction` transactionnelle ou idempotente au rejeu (`DATA-002`). |
| Qualité du code | 8 | `tsc`/`eslint` propres à 100% sur le code applicatif, 0 bloc catch vide, gestion rigoureuse des cas `null`/absence de données, peu de code mort. Limite : quelques fonctions longues (`resolveCalculableBets.ts`, 2561 lignes) et duplications mineures cataloguées. | Découper les fichiers les plus longs, exécuter un outil de détection de code mort/dépendances inutilisées. |
| Sécurité | 8 | 11 des 13 findings de l'audit sécurité antérieur pleinement corrigés et vérifiés indépendamment dans cette session (rotation de clé, CAPTCHA serveur, headers HTTP, timing-safe compare, autorisations explicites, RGPD self-service). Aucune vulnérabilité P0/P1/P2 identifiée. Limite : rate limiting applicatif absent, configuration réelle du dashboard Supabase de production non vérifiable. | Ajouter un rate limiter applicatif de base (`SEC-001`) et confirmer manuellement les réglages Supabase Auth de production. |
| Authentification | 8 | Pattern `getUser()` uniforme, CAPTCHA vérifié serveur, déclaration d'âge, anti-énumération sur reset password. | Autorisations | 9 | Modèle en profondeur rare pour un projet de cette taille (RLS + `SECURITY DEFINER` revalidant systématiquement propriété/`auth.uid()` + triggers d'invariants bloquant l'auto-élévation). Tous les trous applicatifs connus (findings 4/12 de l'audit antérieur) corrigés et vérifiés. | Ajouter des tests d'intégration automatisés qui rejouent les scénarios IDOR/élévation (`TEST-002`) — la robustesse actuelle repose sur la relecture, pas sur un filet automatisé. |
| Intégrité des données | 7 | RLS activée sur 100% des 31 tables (vérifié exhaustivement), contraintes d'unicité logiques bien couvertes, fonctions `SECURITY DEFINER` atomiques par construction. Limite réelle : suppression de compte non transactionnelle (`DATA-002`), un pattern récurrent de migrations correctives après ajout de nouveaux statuts (`DATA-001`), quelques index manquants sur tables secondaires. | Traiter `DATA-002` et `DATA-003` ; ajouter une checklist de revue systématique des index uniques partiels à chaque nouveau statut. |
| Gestion des erreurs | 8 | Pattern de repli cohérent (`null`/`skipped` plutôt qu'un résultat deviné) sur la logique critique (résolution IA). Helper d'erreur générique adopté sur 15/22 Server Actions. Le comportement de panne du micro-service Cloud Run, vérifié le 03/09/2026, s'avère exemplaire (repli `null` uniforme sur 18 fonctions + catch global). Limite restante : 3 fichiers renvoient encore des messages RPC bruts (assumé, documenté). | Généraliser le helper d'erreur générique aux 7 fichiers restants pour clore ce point définitivement. |
| Tests | 5 | Progrès réel et net depuis le dernier bilan interne (2 → 18 fichiers de test, 224 tests, couverture désormais réelle du pipeline IA le plus critique). Mais toujours 0 test de composant, 0 e2e, 0 test d'intégration API, 0 test RLS/permissions, 0 test de concurrence — les scénarios de sécurité et de parcours utilisateur ne sont vérifiés qu'à la main. | Ajouter au moins 5-10 tests e2e sur les parcours critiques et un test d'intégration RLS de base avant de monter au-dessus de 6. |
| UX | 6 | Formulaires soignés (double-submit protégé, erreurs claires, saisie conservée), identité visuelle marquée et différenciante, friction de confirmation bien graduée sur les actions irréversibles. La désync live du Bracket (`BUG-001`) s'avère déjà corrigée depuis le 16/08/2026 (vérifié 03/09) — bon point non crédité dans la version initiale de cette note. Limite nette restante : responsive quasi absent (0 breakpoint Tailwind constaté). | Trancher une position produit sur le responsive desktop. |
| Accessibilité | 5 | Bonne base sémantique (labels, rôles ARIA, `<details>` natif) sur l'échantillon exploré. Lacune concrète et récurrente : absence de piège de focus dans toutes les modales/dialogues, y compris sur les actions les plus critiques. Aucun outil automatisé en CI. | Corriger le focus-trap sur `ModalDialog.tsx` (bénéficie à tous les dialogues qui l'utilisent) et ajouter `eslint-plugin-jsx-a11y`. |
| Performance | 6 | Build de production propre et rapide (~30s), bundle JS d'ordre de grandeur raisonnable (1.6 Mo total, code-splitté), aucun problème mesuré activement dans cette session. Note prudente à 6 (pas 8+) car : toutes les routes sont dynamiques (aucun cache CDN statique), et plusieurs pistes d'optimisation identifiées par un audit interne antérieur n'ont pas été revérifiées ni mesurées avec des outils réels (Lighthouse/Web Vitals). | Mesurer les Web Vitals réels (LCP/CLS/TTFB) dans un vrai navigateur avant de monter cette note. |
| Maintenabilité | 7 | Conventions cohérentes, séparation claire des responsabilités, commentaires expliquant le "pourquoi". Limite : dette de gouvernance implicite (décisions actées "en séance", traçables seulement dans un journal chronologique de 12 000+ lignes), quelques duplications non résolues malgré une factorisation existante. | Résoudre `BUG-002` (migrer les 3 sites non factorisés) et envisager un outil de détection de dépendances circulaires/code mort. |
| Documentation | 6 | Documentation métier/produit exceptionnelle en profondeur (`Cadrage/Suivi/`), mais onboarding technique quasi absent (README générique, pas de `.env.example`) et documentation de suivi non indexée malgré son volume. | Écrire un README réel avec prérequis/variables d'environnement/commandes (`DOC-001`). |
| Déploiement | 6 | CI bloquante en place (lint/typecheck/test/build), déploiement Vercel automatique fonctionnel, secrets correctement séparés serveur/client. Limite réelle : pas de garde-fou de séquencement code/migration (`OPS-004`, déjà rencontré une fois en pratique), pas de `npm audit` en CI. | Intégrer l'application des migrations au pipeline ou une checklist de séquencement obligatoire. |
| Observabilité | 4 | Logs applicatifs structurés existent (`sync_logs`, `audit_logs`) mais consultation manuelle uniquement — aucune alerte proactive, aucun outil d'observabilité externe (Sentry/Datadog), et un risque de panne silencieuse déjà identifié et non mitigé (`heartbeat.yml` auto-désactivable après 60 jours). | Ajouter au minimum une alerte externe (ex. monitoring d'URL type UptimeRobot) sur une route de santé, indépendante de GitHub Actions. |
| Préparation à la production | 7 | Pour le contexte actuel (cercle fermé d'amis, alpha) : niveau de préparation élevé, sécurité et autorisation solides, CI fonctionnelle. Pour une ouverture à un public plus large : rate limiting, observabilité, tests automatisés de permissions, et décision SMTP restent à traiter avant d'être serein sur une montée en charge. | Traiter les 5 anomalies P2 (`DATA-002`, `BUG-003`, `OPS-001`, `TEST-001`, `TEST-002`) avant toute ouverture au-delà du cercle actuel. |

## Moyenne générale (non pondérée) : **6.9/10**

**Lecture** : ce chiffre agrège des axes de nature très différente — la sécurité et les autorisations (8-9/10) sont nettement au-dessus de la moyenne pour un projet de cette taille et de cette vitesse de développement, tandis que l'observabilité et l'accessibilité (4-5/10) tirent la moyenne vers le bas. Cette dispersion reflète fidèlement le diagnostic déjà posé en interne (`BILAN_GLOBAL_01_09_2026.md`) : un niveau d'ingénierie backend/sécurité élevé, avec une couche "produit fini" (tests, observabilité, responsive) qui n'a pas encore rattrapé ce niveau.
